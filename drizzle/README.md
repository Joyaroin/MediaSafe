# Migrations

Generated by `npm run db:generate`, applied by `npm run db:migrate`, committed as plain
SQL. Read the generated file before committing it — that is the point of generating SQL
rather than pushing a schema diff. Editing it by hand is expected; drizzle-kit hashes
each file when it is *applied*, not when it is written.

One history, from one tool, in one order:

| File | What it brings |
| --- | --- |
| `0000_better_auth_tables.sql` | Better Auth's five — `user`, `session`, `account`, `verification`, `rate_limit` (#42) |
| `0001_mediasafe_tables_and_views.sql` | MediaSafe's six, and the three derived-state views (build step 2, #54) |
| `0002_library-entry-remaining-view.sql` | `library_entry_remaining`, the fourth view (#57) |
| `0003_user-import-offer-answered-at.sql` | `user.import_offer_answered_at` |
| `0004_title-external-id.sql` | `title.external_id` — one external id per title (#114) |
| `0005_title-reconciliation.sql` | `title_reconciliation`, the record of a repointed title (#116) |
| `0006_list-membership-title.sql` | `list_membership` repoints from `library_entry` to `title` (#143) |
| `0007_list-membership-drop-library-entry-id.sql` | Drops `list_membership.library_entry_id`, expand-contract's leftover from 0006 (#150) |
| `0008_title-release-date-and-episode-still.sql` | `title.release_date` and `episode.still_path` — ADR-0001 amendment 10 (#246) |

**Name the file after what it brings.** drizzle-kit generates a random tag —
`0005_noisy_maddog` — and the file is renamed, along with its `tag` in `meta/_journal.json`,
before it is committed. The journal is what the migrator reads; renaming one without the other
is a migration that is never applied.

## The hand-edits, and why hand-edits are normal here

`UNIQUE (list_id, position)` on `list_membership` is **`DEFERRABLE INITIALLY DEFERRED`**,
and drizzle-kit did not write that — Drizzle's `unique()` builder cannot express
deferrability at all. It was verified by reading the generated file, added by hand, and
is held there by a test that reads `pg_constraint`.

That is the pipeline working, not a workaround for it. Generating **plain SQL** rather
than pushing a schema diff is what makes an edit like this possible, and drizzle-kit
hashes each file when it is *applied* rather than when it is written, so the edit is
honoured rather than detected. The one thing to know: the edit is invisible to
`meta/0001_snapshot.json`, so a later migration that alters those two columns would drop
the constraint and re-add it without the clause. Put it back by hand if that day comes.

The same reading applies to the views. drizzle-kit emits `CREATE VIEW` **in alphabetical
order**, so `library_entry_up_next` can select from `library_entry_progress` only because
*p* sorts before *u*. A fourth view is a reason to read the generated SQL, not to assume.

### 0006 is the case for reading the generated file, made twice

**drizzle-kit emitted the repoint in an order that cannot run.** It put
`ADD CONSTRAINT … PRIMARY KEY ("list_id","title_id")` *above* the `ADD COLUMN "title_id"`
it depends on. Nothing catches that except reading it: `npm run lint:sql` passes on it,
because a statement referencing a column that does not exist yet is valid SQL, and the
whole run is one transaction, so the failure would have been the deploy. The two
statements are swapped in the committed file and a comment says so.

**And one squawk rule is suppressed in the file rather than in `.squawk.toml`.**
`ban-drop-not-null` fires on `library_entry_id` becoming nullable, and it is right in
general: a column old code trusts to be present should not quietly stop being there.
Here nothing has ever written a row to `list_membership`, and nullable is what
expand-contract *requires* — the column is not dropped in the change that stops using it
(#150 drops it). The suppression is `-- squawk-ignore ban-drop-not-null`, which must be
**the last comment line before the statement**; squawk does not find it through prose
above it. Turning the rule off globally would have been the wrong fix — it stays on for
every other migration.

### 0007 suppresses the rule the whole file exists to enforce

`ban-drop-column` stays on for every migration but this one's actual job: `list_membership`
carried `library_entry_id` nullable and unread since 0006, and #150 is the change that
finally drops it. Suppressed inline, the same way, for the same reason —
`-- squawk-ignore ban-drop-column` as the last comment line before the statement — with the
grep that found nothing referencing the column recorded in the migration's own comment
rather than trusted to memory.

Two things bind everything that lands here:

- **Expand-contract, forward-only** (`SPEC.md` §3, constraint 7). A column is never
  dropped in the change that stops using it. `squawk` is narrowed to destructive rules
  and fails on a dropped column or table, which is what makes that mechanical rather
  than remembered. Neon Free keeps six hours of history and a restore overwrites the
  branch, so this is the actual protection for the data, not a rollback policy.

  Run it before you commit: `npm run lint:sql`. The narrowing lives in `.squawk.toml`,
  where every rule that is *off* carries the reason it is off — including
  `require-concurrent-index-creation`, which is off because it contradicts the paragraph
  below.
- **The whole pending run is one transaction.** Drizzle's migrator opens it — see the
  note at the top of `db/migrate.ts` and the test that holds it true. The consequence
  that bites: **statements Postgres forbids inside a transaction block cannot be used
  here.** `CREATE INDEX CONCURRENTLY` is the one build step 2 will reach for; use the
  plain locking form instead, on a library of 472 titles where the lock is imperceptible.
